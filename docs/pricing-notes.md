## 2. 峰谷判定精确规则

### 2.1 规则正文

1. **时区**：一律按 **Asia/Shanghai（UTC+8，北京时间）** 判定。**不**使用客户端本地时区、**不**使用 UTC。证据：E2「高峰时段为北京时间 9:00-12:00、14:00-18:00」；E3 给出等价的 UTC 口径（详见 §2.3）。
2. **高峰时段**：北京时间 **周一至周五**（不含中国法定节假日）的
   - `[09:00, 12:00)` 与 `[14:00, 18:00)`
3. **空闲时段（谷价）**：以上之外的一切时刻，具体包括
   - 工作日 00:00–08:59、12:00–13:59、18:00–23:59
   - **周六、周日全天**（自北京时间 2026-08-23 00:00 起生效，E7）
   - **中国法定节假日全天**（自北京时间 2026-09-19 00:00 起适用，E8）
   - **调休上班的周末**同样按谷价（因为首先落在周末，E8「调休上班的周末…均按空闲时段计费」）
4. **生效时间线**
   - 2026-08-17 00:00（北京时间）：峰谷定价机制正式实施（E2/E4）
   - 2026-08-23 00:00：周末两天全天改按谷价，不再区分峰谷（E7）
   - 2026-09-10 11:00 起（报道称「9 月 10 日中午起执行」）：Flash 系列降价至 0.02 / 1 / 4 谷价档（E9/E10/E11）
   - 2026-09-19：官方明确「调休上班的周末 + 法定节假日全天」也按空闲时段（E8）

### 2.2 边界判定（易错处，务必按此实现）

区间为**左闭右开**：

| 时刻（北京时间，工作日） | 判定 | 说明 |
|---|---|---|
| 08:59:59.999 | 谷 | |
| **09:00:00.000** | **峰** | 9 点整**算高峰**，`hour >= 9` 即命中 |
| 11:59:59.999 | 峰 | |
| **12:00:00.000** | **谷** | 12 点整**算谷**，`hour < 12` 不满足 |
| 13:59:59.999 | 谷 | |
| **14:00:00.000** | **峰** | 14 点整**算高峰** |
| 17:59:59.999 | 峰 | |
| **18:00:00.000** | **谷** | 18 点整**算谷** |
| 周六/周日任意时刻 | 谷 | 含调休上班日 |
| 法定节假日任意时刻 | 谷 | 含落在工作日内的节假日 |

**一句话概括：`峰 = 工作日 && (9≤h<12 || 14≤h<18)`。**

其他边界说明：

- **12:00–14:00 午间低谷**：常被误解为峰，实际是谷，占满 2 小时，务必分段处理。
- **节假日与调休**：以国务院办公厅年度通知为准。节假日**全天**谷价（含其内部的 9–12、14–18 点）。调休上班日若落在周末 → 按周末谷价；若落在工作日（2026 年没有这种情况）→ 仍按工作日峰谷规则。
- **判定优先级**：先判周末/节假日（直接谷）→ 再判小时窗口。否则「国庆节周四是工作日」会被误判为峰。
- **不可回溯**：2026-08-17 之前的调用不适用本表（峰谷机制未生效，且价格不同）。历史对账须按月/版本分档，不能用现行规则重算。同理 8-23 前周末无优惠、9-10 前 Flash 是旧价。
- **节假日表需每年维护**：2026 年的 11 月国务院发布 2027 年安排后必须补录，否则 2027 年节假日会被误判为高峰。

### 2.3 时区换算自检（强佐证）

E3 给出的 UTC 口径与本表的北京时间口径**完全吻合**，这是本次核实中最有力的独立交叉验证：

| 段 | 北京时间 | UTC |
|---|---|---|
| 上午峰 | 09:00–12:00 | 01:00–04:00 |
| 下午峰 | 14:00–18:00 | 06:00–10:00 |

若某实现按 UTC 判定，写成 `01:00–04:00 / 06:00–10:00` 即可等价；**切勿**把 UTC 时间戳直接套北京小时数。

### 2.4 跨天 / 跨边界如何枚举

- **逐桶计价**：一个请求若跨越峰谷边界，不能按「请求开始时刻」一刀切，应按**分段（桶）时间戳**分别判定峰谷再加权。本机插件即按 epoch 秒分桶后逐桶 `isPeakTime()`。
- **推导下一个切换点**：只需扫北京时间的 `0 / 9 / 12 / 14 / 18` 点边界。本机 `nextPeakChangeAt()` 扫未来 12 天（覆盖最长 9 天春节假期）留足余量。
- **有单片时间但无分桶时**：若上游只给「一个开始时间 + 总 token」，只能：① 保守按峰价；或 ② 按耗时跨边界比例分摊并**明确标注为估算**。不要静默按谷价（会低报）。
- **JSONL 中同一轮可能多条 usage 记录**：应按每条记录自身 timestamp 计价后再求和，不要在会话结束时用最后一条的时间统一计价。

## 3. 金额公式

### 3.1 单次调用（单一计费时段）

```
cost_yuan = ( hitTokens * p_hit + missTokens * p_miss + outTokens * p_out ) / 1_000_000
```

其中 `[p_hit, p_miss, p_out]` 取该调用时间戳所对应时段的价三元组（谷或峰），例如 Flash 谷价 `[0.02, 1, 4]`、Flash 峰价 `[0.04, 2, 8]`。

### 3.2 跨时段调用（分段求和）

```
cost_yuan = Σ_i ( hit_i * p_hit(t_i) + miss_i * p_miss(t_i) + out_i * p_out(t_i) ) / 1_000_000
```

`t_i` 为第 i 个分桶的时间戳，`p_*(t_i)` 按 §2 规则由 `t_i` 决定。

### 3.3 `cacheWriteTokens` 是否单独计价？—— **不单独计价**

**结论：DeepSeek 的 prompt cache 写入不设独立价目，不额外收费。**

依据（按强度排序）：

1. **价目表结构证据**：官方计费项只有三档 —— 缓存命中输入、缓存未命中输入、输出。Pro 与 Flash 两档模型的价格表都只有 `hit / miss / out` 三项，**不存在 cache-write 价格项**（本机注释与检索到的报道口径一致，报道只讨论「缓存命中/未命中/输出」三档，未见任何「缓存写入」计费项）。
2. **机制推断**：缓存写入发生在「未命中」路径上，该次输入已按 `miss` 价计费一次，写入不另收。这与 Anthropic 的「cache write 溢价（如 1.25×）」模型**根本不同**。
3. **反向检索无证据**：多次以「缓存写入 是否收费 / cache write」为关键词检索，命中的全是「缓存命中降价」「缓存输入 0.02 元」一类报道，**没有任何** cache write 独立计价的报道。

**可信度：中高（三星）**。属「价目表结构 + 机制惯例 + 检索无相反证据」的综合判断，**未取得官方条文正面表述**。

**实现要求**：

- 若上游把 `cache_creation_input_tokens` / `cacheWriteTokens` 单独给出，应 **并入 `missTokens` 按 miss 价计费**，不要建第四档价格。
- 若同时存在 `cache_hit` 与 `cache_miss` 字段且合计等于 `prompt_tokens`，直接各用各的；避免重复计入。
- **切勿照搬 Anthropic 式公式**（`cacheWrite × 1.25 × input`），会显著高估费用。

### 3.4 精度与四舍五入建议

**推荐方案：整数「纳元×10」累加，仅在展示时格式化。**

价格与 token 数都可精确整数化：

```
price 均为 0.01 的倍数，tokens 为整数
→ tokens * price 是 0.01 的倍数（单位：元 × 1e-6 即「微元」）
→ 令 units = Σ tokens_i * price_i * 100    // 整数，单位 1e-8 元
→ cost_yuan = units / 1e8
```

`units` 全程为整数，**无浮点累积误差**，可实现「逐轮累加后与官方账单严格对得上」。

示例：输出 12345 token，Flash 谷价 4 元/M → `12345 * 4 * 100 = 4,938,000` units = `0.04938` 元。

**展示建议**：

| 场景 | 精度 | 示例 |
|---|---|---|
| 每轮对话费用 | 4 位小数（0.0001 元） | `¥0.0049`；不足 0.0001 时显示 `¥<0.0001` |
| 会话累计 / 今日累计 | 2 位小数（分），或统一 4 位 | `¥1.23` |
| 账户余额 | 2 位小数 | `¥12.34` |

**纪律**：

- **只在最终展示时舍入**，绝不在累加过程中舍入（否则 N 轮会累积偏差）。
- 舍入方式用普通四舍五入（`Math.round`）即可；本场景无「银行家舍入」需求。
- 若必须用浮点（float64）实现，也够用：单 token 最小金额约 `2e-8` 元，float64 有效位 ~15–16 位，误差远小于展示精度；但仍建议整数 units 方案以避免长期累计漂移。
- 不要用 `toFixed()` 的结果再参与后续加法。

## 4. 可疑点与不一致之处（**重点，插件实现请务必看**）

### 4.1 「Pro 是 Flash 的 3 倍价」这句注释已过时，但数字本身自洽

本机注释写「Pro 为 Flash 的 3 倍价（官方 2026-08-17 生效）」。用现行 Flash 价（0.02 / 1 / 4）去算，比值是：

- hit：0.15 / 0.02 = **7.5×**
- miss：4.5 / 1 = **4.5×**
- out：13.5 / 4 = **3.375×**

**三档都不等于 3 倍** —— 若据此「按 3 倍推算」，会算错。

但对照 **2026-09-10 降价前**的 Flash 价（0.05 / 1.5 / 4.5，见本机注释）：

- hit：0.15 / 0.05 = **3.0×**
- miss：4.5 / 1.5 = **3.0×**
- out：13.5 / 4.5 = **3.0×**

**三档严格 3 倍。** 同时 E12「DeepSeek V4 Pro 正式版上线：价格比 Flash 贵三倍」与该历史关系吻合。

**判定**：Pro 的 `0.15 / 4.5 / 13.5` 三档数字有**强内部自洽性**（相对旧 Flash 价严格 3 倍），且输出峰价 27 已被官方公告转述直接证实（E2），故这组数字可信度实际上**高于**「仅凭一句注释」。但「3 倍」这一表述在 9-10 降价后已失效，属**注释滞后**，不是数据错误。

**对插件的硬性结论：不得用「主价 × 倍数」推算任何价格，必须使用绝对价表。** 倍数关系只是历史校验手段。

### 4.5 本机实现的规则正确性复核

逐行复核 `isPeakTime()`（第 643–658 行），**逻辑正确**：

- `bj = new Date(n*1000 + 8*3600*1000)` 后取 `getUTCDay()/getUTCHours()` = 正确取得北京日历日与小时（未误用本地时区）。
- `hour >= start && hour < end` → 左闭右开，与 §2.2 边界表一致。
- 周末判定带 `WEEKEND_VALLEY_FROM_SEC = Date.UTC(2026,7,22,16,0,0)` = 北京 2026-08-23 00:00 ✓。
- 节假日判定带 `HOLIDAY_VALLEY_FROM_SEC = Date.UTC(2026,8,18,16,0,0)` = 北京 2026-09-19 00:00 ✓，且 `isHolidayValley` 用平移后的 `toISOString().slice(0,10)` 取北京日期 ✓。
- `nextPeakChangeAt()` 只扫 `0/9/12/14/18` 边界，扫 12 天，与 `isPeakTime` 同源 ✓。

**唯一实质隐患：`HOLIDAY_VALLEY` 是 2026 年硬编码表（第 620–630 行）。** 2027 年起若不补录，节假日会被误判为高峰（每个假期每个工作日上午 9–12、下午 14–18 会多收一倍）。移植到新插件时，建议：
- 保留可维护的节假日表 + 一个「表未覆盖当年」的启动告警；
- 或改为从外部配置/接口读取。

## 7. 给插件实现的 8 条硬性检查项

1. 时区固定 `Asia/Shanghai`，用 epoch → `+8h 后按 UTC 读`，禁用本地时区。
2. 区间左闭右开；`9:00` 峰、`12:00` 谷、`14:00` 峰、`18:00` 谷。
3. 先判周末/节假日（→谷），再判小时窗口。
4. `cacheWriteTokens` 并入 `missTokens`，**不设第四档价格**。
5. 用绝对价表，**不用倍数推算**；「Pro = 3×Flash」已过时。
6. 逐桶时间戳计价，跨边界不得一刀切；无分桶时按峰价保守估算并标「估算」。
7. 整数 units 累加（`units = Σ tokens × price × 100`，单位 1e-8 元），仅在展示时舍入到 0.0001 元。
8. UI 标注价格快照日期（2026-09-19）+ 提供自定义单价覆盖 + 节假日表当年未覆盖时告警。
9. **Search/Fetch 按次计费必须带生效线闸门**：以**请求发起时刻**（tool/call 的 time）与北京 2026-11-01 00:00 比较，之前的调用计 0 元；失败请求（tool/result 带 isError/error）不计次；单价 500,000 units/次，不分峰谷。

## 8. Search/Fetch 在 DSH 会话日志里的形状（计费语义核实）

> 2026-10-25 用本机 73 份真实会话日志实测核实（脚本逻辑并入 `test/live-ledger.mjs`）。

### 8.1 Search：一次 `web_search` 工具调用 = N 次 Search API 请求

- 模型发 `tool/call`（`name: "web_search"`），`arguments` 形如 `{"queries": ["q1", "q2"]}` —— **每个子查询各发一次 Search API 请求**。
- 每次真实请求在日志里留一条 `web/deepseek-search-llm-request` 事件（body 带 `tools: [{type: "web_search_20250305", max_uses: 5}]`，打到 `api.deepseek.com/anthropic/v1/messages`）。
- **本机实测：35 次调用 / 59 个子查询 = 59 条请求事件，严格相等**。所以「子查询数」是「请求次数」的可靠代理。
- 计费口径取**子查询数**（而非请求事件数），因为客户端 Chat 快照看不到 `web/deepseek-search-llm-request`（它是宿主侧事件）；两边口径一致才能保住「每轮之和 = 会话总额」。请求事件数保留为 `searchApiEvents` 诊断字段，`live-ledger` 交叉核对。
- 调用失败（tool/result 带 isError）→ 整次调用的子查询全部不计。

### 8.2 Fetch：`tool/call(name="web_fetch")` + `tool/result`

- 成功：tool/result 无 `isError` / `error` → 计 1 次（本机 61 次调用中 27 次成功）。
- 失败：tool/result 带 `isError: true` 与 `error: {name: "WebError", code: "WEB_PROVIDER_ERROR"}`（本机 34 次，多为网络不通）→ 不计。
- 官方 `@deepseek-ai/dsh-client-ui-chat` 的 `rootResult` 投影同样以 `message.isError === true` / `event.data.error` 为失败信号 —— 客户端 `tool-call` 节点的 `data.root`（`kind: "tool-result"`）与宿主事件口径天然一致。

### 8.3 客户端可见形状（`dsh-client-ui-chat` 投影，v 源码核实）

- 节点：`{kind: "tool-call", location: {kind: "step"|"turn", turn: {turn: N}}, data: {root}}`。
- 出结果后 root：`{kind: "tool-result", name, callId, callTime（发起时刻）, time（完成时刻）, isError, error?, call: {argsRaw}}`。
- 进行中的调用 root 是 `{phase: "start", ...}`（无结果）→ 不计。
- 轮次归属用 `location.turn.turn`（结果 root 自身不带 turn 字段，这是当初差点踩的坑）。
